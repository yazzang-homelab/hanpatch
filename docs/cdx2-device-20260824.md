The build in this ledger is `c13de82c4836c41aaac976ad329f882d1a2abb4cb6321b8df1e9e0a4ec3dc385`
(`Classic Dungeon X2 (ko).iso`, 550,699,008 bytes, published to

the build machine). `hanpatch loop gate` reported `ok:true` at iteration 147 for

Captured on the owner's device: AYN Thor v33 (arm64), PPSSPP v1.19.3 release,
JIT, no cheats, no plugins, disc id `NPJH50388`. 14 screenshots, sha256 recorded
in `evidence/device-20260824/SHA256SUMS.txt` on the build machine. The images are
NOT in this repository - the repository tracks text and policy only - so every

**Reading rule for this ledger.** "Sealed" is what `loop/sealed-text.json` holds.

## D1 - New Game crashes after the appearance grid (blocker)

`Screenshot_20260824-233043.png`. PPSSPP's own crash screen:

```
Bad Execution Address
NPJH50388, v1.19.3 (release), CRC 479a60be (not identified)
Destination: CPU Jump to 9d718c30
PC: 9d718c30    RA: 0893d338
Cur thread: user_main (attr 800040ff)
```

Sequence: title -> New Game -> BGM prompt -> prologue -> character creation ->
name entry -> job list (`Screenshot_20260824-233013.png`) -> appearance grid
(`Screenshot_20260824-233020.png`) -> crash. The job list and the appearance grid
both render, so the crash is at or just after the confirm on the appearance grid.

`PC: 9d718c30` is not code: it is a jump to an address the loader never mapped,
which is the same shape as the crash fixed on 2026-08-23 - a record whose SOURCE
named an archive member (`OPENING.LDT`) was translated, so the loader returned
null and the game jumped through it. `FINDINGS-newgame-crash.md` on the build
machine records that fix and the archive-membership rule that now blocks it. That
rule is necessary, and this crash proves it is not sufficient: something on the
character-creation path is still being written where the engine expects an
operand. `RA: 0893d338` is the return address to bisect from.

Do not assume it is the same class without checking. The alternative is the font:
D2 shows the shipped font sheet and the shipped text disagree about cell
assignment, and a character-creation screen that indexes a glyph table by
computed cell is a plausible second cause.

## D2 - Drawn glyph is the neighbouring cell for a subset of syllables

The sealed text is correct and the screen is wrong. Measured pairs, with the cell
codes and the sort ranks from `work/font_map.json` (1172 retargeted cells,
codes 35032-37300):

| sealed | drawn | code delta | rank delta |
|---|---|---|---|
| 을 (36563) | 은 (36560) | -3 | -1 |
| 할 (37193) | 한 (37190) | -3 | -1 |
| 생 (36211) | 샘 (36210) | -1 | -1 |
| 결 (35178) | 견 (35177) | -1 | -1 |

Instances:

- `db__STRTBL.DAT/s445` seals `무엇을 할까?`; the device draws `무엇은 한까?`
  (`Screenshot_20260824-232938.png`).
- The same screen seals `캐릭터 생성` and draws `캐릭터 샘성`.
- `db__STRTBL.DAT/s449` seals `직업을 고른다. ⑩결정 ⑪뒤로`; the device draws
  `직업은 고른다.` with `견` for `결` (`Screenshot_20260824-233013.png`).
- The name-entry help line seals `캐릭터의 이름을 정한다.` and draws
  `캐릭터의 이름은 정한다.` (`Screenshot_20260824-232942.png`).

For every measured pair the drawn syllable is the one exactly ONE RANK EARLIER in
the sorted cell map. It is not a global off-by-one: `정`, `고`, `른`, `다`,
`캐`, `릭`, `터` all draw correctly on the same lines, and their rank-1
neighbours (`접`, `계`, `르`, `닝`) do not appear anywhere. So a subset of cells
holds the previous glyph in the sequence - consistent with a baker that writes a
glyph, fails to advance its free-cell cursor, and writes the next glyph into the
same cell, leaving the intended cell holding its predecessor. `work/font_map.json`
and `work/FONT1.ARC`/`FONT2.ARC` were all written at 2026-08-20 22:24, while the
text was resealed on 08-23 and 08-24; whether the shipped sheet was rebaked for
the current charset is the first thing to establish.

The authority for this is `glyph_authority: build` in the profile and
`tools/cdx2_font.py`, which derives the charset from the sealed text and bakes
the sheet. Whatever the cause, the fix belongs there and in the readback that
`hanpatch verify` performs - a readback that compares text bytes but never
compares a cell's bitmap to the syllable the map claims it holds will keep
passing this defect.

## Not defects

- The kana grid on the name-entry screen stays Japanese. That is the profile's
  `skip_keys` decision, recorded there: the two EBOOT rows are a fixed
  102-cell coordinate grid, translating them breaks name entry, and Hangul entry
  needs jamo composition the engine cannot do. Leave it alone.
- `CRC 479a60be (not identified)` on the crash screen is PPSSPP's compatibility
  database not recognising a patched disc. It is not evidence of a bad dump.

## Why the gate passed

The profile declared no `runtime_evidence`, so `RUNTIME_SMOKE` was `NOT_RUN`, and
`NOT_RUN` does not block. The profile now declares
`evidence/runtime/newgame.json`, and `tools/runtime_gate.sh` replays
`tools/route.newgame.txt` on a headless PPSSPP to produce that document bound to
the built ISO's sha256. A rebuild changes the hash, which invalidates the old
document, so runtime proof cannot be inherited from a previous build.

That gate proves the game does not fault along the route. It cannot read the
screen, so D2 through D7 are not observable by it - they need the static gates,
the font readback, and human eyes on the frames it captures.

## What to fix, in this order

**D1, the blocker.** New Game crashes at the end of character creation:
PPSSPP reports `Bad Execution Address`, `CPU Jump to 9d718c30`, `RA 0893d338`,
thread `user_main`. A jump to an unmapped address is the same shape as the crash
fixed on 2026-08-23, where a record whose SOURCE named an archive member
(`OPENING.LDT`) had been translated and the loader returned null. The
archive-membership rule in `hanpatch/adapters/cdx2.py` blocks that exact case and
is demonstrably not sufficient. Find what else on the character-creation path is
written where the engine expects an operand - or prove the cause is the font
(D2), which is the other candidate the ledger names. State which one it is with
the evidence that decided it.

**D2, glyph cell drift.** The sealed text is correct and the screen is wrong:
`db__STRTBL.DAT/s445` seals `무엇을 할까?` and the device draws `무엇은 한까?`.
For every measured pair the drawn syllable is the one exactly one rank earlier in
the sorted cell map of `work/font_map.json` (을→은, 할→한, 생→샘, 결→견), while
other syllables on the same line draw correctly. `tools/cdx2_font.py` derives the
charset from the sealed text and bakes the sheet; the profile declares
`glyph_authority: build`. Fix the cell assignment, and add the readback that
would have caught this: a check that compares the bitmap in a cell to the
syllable the map claims that cell holds. A round trip that compares text bytes
and never looks at a glyph will keep passing this defect.

**D3, retargeted cells that Japanese text still references.** A `特` is drawn
inside the kana palette grid, and the `movable_tags` icon glyphs (`①`-`⑳`) draw
the original Japanese words `決定 / 情報 / 装備替` over the Korean line. The
profile's claim that 1493 cells are free because nothing on the disc renders them
is contradicted by the screen. Establish which cells are genuinely free and make
the baker refuse to retarget one that is referenced.

**D4, the prologue narration is untranslated.** Six Japanese lines, quoted in the
ledger, are the first text a player reads and are not in the Korean corpus. After
the operand rule, `OPENING.LDT` is correctly refused - the narration text itself
still has to be extracted from whatever container holds it. Find the container
and make `extract` emit it. Do not write Korean for it in this job: the text
belongs to the title repository, and the second job in this batch handles text.

## Rules

- An adversarial test per fix, in the existing standalone-script style
  (`python3 tests/test_x.py`, not pytest cases - pytest's collection imports them
  and their module-level `sys.exit` aborts the run). `tests/test_cdx2_font.py`,
  `tests/test_cdx2_operand.py` and `tests/test_runtime_evidence.py` are the
  nearest models. A gate without a test that fails without it is not a gate.
- Never widen a gate, a budget or a waiver to make a build pass.
- `pyproject.toml`, `LICENSE`, `NOTICE.md` and `.github/` are protected and must
  not appear in your diff.
- Run `run_checks` with the `unit` suite before publishing. It runs the
  corpus-free test scripts through `tools/check_suite.sh` and takes about a
  minute.
- Publish with `publish_pull_request` using Conventional Commits. Do not open a
  second task for the same work.

## Acceptance

fix for each defect you claim to have fixed, and your completion summary names
for each of D1-D4 either the fix or the reason it is not fixable in this package
- with the measurement behind that reason. "Could not reproduce" is a valid
