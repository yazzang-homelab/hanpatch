# 독자 피드백과 수정 작업지시서

대본집을 읽는 사람이 이상한 번역을 그 자리에서 지적하고, 운영자가 그 지적을 모아
수정 작업지시서로 묶고, 승인한 지시서만 실제 번역에 반영되는 경로다.

핵심은 분리다.

- **독자**는 대사마다 붙은 `의견` · `공감` 버튼과 검색창만 본다. 처리 상태, 다른
  사람의 신원, 내부 메모는 어느 응답에도 들어가지 않는다.
- **운영자**는 사설대역에서만 열리는 내부 화면에서 분류하고, 지시서에 **이름을
  남겨 승인**한다.
- **번역 반영**은 CLI 한 곳뿐이고, 승인되지 않은 지시서와 지시서에 없는 키는
  거부한다. 에이전트가 독자 의견을 읽고 스스로 번역을 고치는 경로는 없다.

마지막 항목은 코드 게이트가 붙은 절차이지 보안 경계가 아니다. root 권한이 있는
프로세스는 언제든 `text_ko.json` 을 직접 쓸 수 있다. 게이트의 목적은 자동화된
단계가 낯선 사람의 코멘트를 사람 없이 탑재 텍스트로 바꾸지 못하게 하는 것이다.

## 켜는 방법

`hanpatch.json` 에 API 주소를 적으면 대본집이 위젯과 전체 검색을 싣는다. 적지
않으면 대본집은 예전처럼 완전한 정적 문서로 생성된다.

```json
{ "feedback_api": "/dq7/api" }
```

치환 토큰의 화면 표기는 프로필에 선언한다. 검색 렌더링에만 쓰이고 탑재 텍스트는
토큰을 그대로 유지한다. 선언하지 않은 토큰은 검색 렌더링에서 지워진다 — 없는
표기를 코드가 만들어 내지 않는다.

```json
{ "placeholder_text": { "{HERO}": "아루스", "{GABO}": "가보" } }
```

```
hanpatch feedback index                     # 대본 전체를 검색 색인에 넣는다
hanpatch feedback serve --port 8120 \
  --admin-port 8121 --token-file /etc/dq7-feedback.token \
  --db work/feedback.db --orders work/orders
hanpatch book                               # 위젯이 실린 대본집을 다시 만든다
```

색인은 대본집이 실제로 렌더링하는 행만 담는다. 검색 결과의 링크가 항상 존재하는
쪽으로 가야 하기 때문이다. `hanpatch gates` 로 매니페스트를 다시 봉인했으면
`feedback index` 를 다시 돌린다.

## 검색

한 질의가 원문과 번역을 동시에 본다.

- **부분 일치.** 세 글자 이상은 trigram FTS5 로, 한두 글자는 LIKE 스캔으로 찾는다.
  단어 중간에 걸리는 조각도 잡힌다(`신상에`, `oddes`).
- **화면 렌더링.** 컨테이너의 행은 템플릿이다. `{HERO}는 {I_NAME}을 받았다!` 는
  화면에 그 글자로 나오지 않으므로, 선언된 치환값을 넣은 문장(`아루스는 을
  받았다!`)도 같은 열에 색인한다. 아이템 메뉴의 `안초비;모래` 처럼 필드 구분자로
  쪼개진 이름은 구분자를 뗀 형태도 색인한다.
- **문장 검색 폴백.** 화면에서 베낀 문장은 여러 행에 걸쳐 있어 어떤 한 행과도
  일치하지 않는다(아이템 이름은 다른 행이다). 그럴 때는 단어로 쪼개서 **일치한
  글자 길이 순**으로 보여 준다. AND 는 정작 이 경로가 필요한 질의에서 0건이 되고,
  점수 없는 OR 은 `받았다` 가 들어간 모든 행에 묻힌다. 긴 고유 단어가 흔한 단어
  둘보다 무겁다.

## 독자가 보는 것

대사 블록 아래의 `의견` 은 그 대사의 지적 목록과 입력 폼을 연다. 유형(오역 ·
어색함 · 오타 · 이름 표기 · 줄바꿈 깨짐 · 말투 · 기타), 내용, 고칠 문장 제안,
이름(선택). `공감` 은 IP 해시당 한 번 토글된다.

- 이름은 필수가 아니다. 원문 IP 는 저장하지 않고 서버가 만든 솔트로 해시만 남긴다.
- 자기 글은 지시서에 묶이기 전까지 `내 의견 지우기` 로 지운다. 권한은 게시할 때
  받은 토큰뿐이고 그 토큰은 그 브라우저에만 있다.
- 게시 예산은 IP 해시당 1분 3건 · 1시간 15건 · 1일 60건이고, 같은 대사에 10분 안
  재게시는 중복으로 막는다. 사람이 보지 않는 필드(허니포트)가 채워지면 200 을
  주고 저장하지 않는다.
- 다른 사람이 쓴 글은 `textContent` 로만 그려진다. 마크업이 마크업이 되는 경로가
  없다.

## 운영자가 하는 것

내부 화면(`/admin/`)에서:

1. 대기 큐를 읽는다. 항목마다 원문 · 현재 탑재된 번역 · 지적 · 제안 · 공감 수가
   같이 보인다.
2. 채택 / 보류 / 반영 안 함 / 중복으로 분류하고 메모를 남긴다. 이 어휘는 독자
   응답에 절대 나가지 않는다.
3. 선택한 항목으로 **지시서 초안**을 만든다. 초안은 대상 행의 원문과 현재 번역을
   그 시점 그대로 얼려 담고, 독자 신원은 담지 않는다.
4. 검토한 뒤 **승인**을 누르고 이름을 적는다. 그 이름이 지시서에 남는다.

승인하면 `orders/<ID>.json` 과 사람이 읽는 `orders/<ID>.md` 가 쓰인다. `.md` 는
번역자나 에이전트에게 그대로 건네는 지시문이고, 첫 화면에 승인자와 작업 규칙이
있다. 미승인 지시서에는 **아무것도 수정하지 말 것** 이 박혀 있다.

## 반영

수정문은 `{"패밀리/키": "새 번역"}` 형태의 JSON 으로 받는다.

```
hanpatch feedback apply ord-20260812-072946 --fixes fixes.json
```

이 명령은 다음을 거부한다.

- 승인되지 않은 지시서 (`draft`), 폐기된 지시서, 이미 반영된 지시서
- 지시서가 열거하지 않은 키
- 매니페스트 빌드와 **같은 룰셋**(용어집 · 용량 · 줄바꿈 · 태그 다중집합)을
  통과하지 못하는 값. 이때는 무엇이 걸렸는지 출력하고 파일을 쓰지 않는다.

통과하면 값이 `work/<대상어>/text_ko.json` 오버라이드에 들어가고, 해당 피드백은
`done` 이 된다. 그다음은 평소와 같다 — `hanpatch gates` 로 다시 봉인하고,
`hanpatch build`, 그리고 `hanpatch feedback index` 와 `hanpatch book` 으로 대본집을
갱신한다.

## 배치 (DQ7)

| 대상 | 위치 |
| --- | --- |
| 공개 API | `krpatch.duckdns.org/dq7/api/` → `127.0.0.1:8120` |
| 내부 처리 화면 | 사설대역 vhost `:8100/admin/` → `127.0.0.1:8121` |
| DB | `/mnt/ssd256/dq7-feedback/feedback.db` |
| 승인된 지시서 | `/mnt/ssd256/dq7-feedback/orders/` |
| 서비스 | `dq7-feedback.service`, `dq7-feedback-index.timer` (매일 04:20) |

정적 vhost 는 여전히 `GET`/`HEAD` 만 받는다. 쓰기 경로는 `/dq7/api/`(피드백)와
`/dq7/api/cheer`(응원 메시지) 두 곳뿐이고, 그래서 메서드 제한이 server 단 `if` 에서
location 단 `limit_except` 로 바뀌었다 — server 단 `if` 는 모든 location 에 적용되어
한 곳만 열어 줄 수 없다. 내부 화면의 토큰은 600 권한 스니펫에서 주입되므로 URL 에
남지 않는다.

## 후원 링크

피드백이 늘면 확인하는 사람의 시간도 늘어난다. `hanpatch.json` 에 후원 페이지
주소를 적으면 대본집 머리글에 `☕ 후원하기` 링크가 붙고, 첫 쪽에 후원 안내 문단이
하나 들어간다. 적지 않으면 링크도 문단도 생성되지 않는다 — 후원 대상은 배치하는
사람의 결정이고, 코드가 정해 둘 값이 아니다.

```json
{ "donate_url": "/dq7/donate.html" }
```

DQ7 배치에서 그 경로는 후원 vhost(`127.0.0.1:3000`, `/var/www/coffee-hanzan`)를
`krpatch.duckdns.org` 뒤로 프록시한 것이다. 후원 페이지는 `emulog.app` 과 같은
파일·같은 접수 API(`127.0.0.1:3001`)를 쓰고, nginx 가 `X-Cheer-Site` 로 어느 쪽에서
온 응원인지만 구분해 준다. 후원 페이지 · 응원 폼의 링크는 모두 상대 경로라서 루트
(`/donate.html`)와 하위 경로(`/dq7/donate.html`) 양쪽에서 그대로 동작한다.

| 대상 | 위치 |
| --- | --- |
| 후원 페이지 | `krpatch.duckdns.org/dq7/donate.html` → `127.0.0.1:3000` |
| 응원 폼 · 목록 | `/dq7/donate-message.html`, `/dq7/supporters.json` |
| 응원 접수 | `/dq7/api/cheer` → `emulog-cheer.service` (`127.0.0.1:3001`) |
| 승인 | 텔레그램 버튼 · `approve.py` → `/var/www/coffee-hanzan/supporters.json` |

응원이 접수되면 운영자 텔레그램으로 `✅ 승인` / `🚫 보류` 버튼이 달린 알림 한 통이
가고, 버튼을 눌러야 벽에 올라간다. 자동 게시는 없다 — 입금 내역을 볼 수 있는 것은
사람뿐이고, 잔 수 버튼은 3천 원 배수만 있어서 실제 입금액과 달라질 수 있다. 금액을
정정해서 게시하려면 알림에 `승인 5000` 처럼 답장한다.

| 설정 | 위치 |
| --- | --- |
| 봇 토큰 · 알림 대상 · 승인 시크릿 | `/etc/emulog-cheer.env` (0600) |
| 봇이 읽는 승인 시크릿 | `/etc/emulog-cheer.secret` (0600) |
| 버튼을 받는 곳 | `commander-ng-telegram.service` (이 봇 토큰의 유일한 getUpdates 소비자) |
| 승인 엔드포인트 | `127.0.0.1:3001/api/approve` (nginx 밖으로 노출 안 함) |

알림은 부가 기능이다. 토큰이 없거나 텔레그램이 죽었다면 접수는 그대로 성공하고,
`approve.py list` / `approve.py ok <항목> [금액]` 로 같은 큐를 처리한다.
