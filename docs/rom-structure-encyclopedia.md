# 롬 구조 분석 백과사전 및 방법론

레트로 콘솔 롬에서 텍스트·폰트·포인터 구조를 찾아내는 방법의 정리.
모든 항목에 **증거 등급**을 붙였다. 등급 없는 문장은 이 문서에 없다.

| 등급 | 뜻 |
|---|---|
| `measured` | 이 워크스테이션에서 직접 실행·계수해 확인 |
| `documented` | 제3자 산출물에 기록됐고 내부 정합성을 확인 |
| `derived` | 위 둘에서 공식·정의로 유도 |
| `asserted` | 관행·통설. 반증되지 않았을 뿐 |

---

## 0. 왜 이 문서가 필요한가

롬 한글화의 실패는 대부분 번역이 아니라 **구조 오독**에서 난다.
그리고 구조 오독은 거의 항상 같은 뿌리를 갖는다 — **파일명·라벨을 사실로 취급**한 것.

`measured` 이 프로젝트에서 실제로 겪은 라벨 거짓 2건:

- `(K) Super Mario Advance 2` 로 표기된 파일이 일본판과 SHA-256 **완전 일치**. 한글패치가 아니었다.
- `RoboCop Versus The Terminator.nes` 의 내용물이 실제로는 **Robocco Wars**.

그래서 이 문서의 제1 규율은 하나다.

> **내용 SHA-256만이 신뢰 축이다. 파일명은 힌트이지 지표가 아니다.**

---

## 1. 총론 — 롬을 읽는 네 개의 축

어떤 플랫폼이든 텍스트를 찾는 문제는 네 축으로 분해된다. 축을 섞으면 반드시 오탐이 난다.

| 축 | 질문 | 틀렸을 때 증상 |
|---|---|---|
| **주소공간** | 포인터가 가리키는 숫자를 파일 오프셋으로 어떻게 바꾸나 | 포인터 테이블을 찾고도 텍스트가 안 나옴 |
| **인코딩** | 바이트 → 글자 대응이 무엇인가 | 텍스트를 찾고도 못 읽음 |
| **포인터** | 테이블의 엔트리 폭·배치·값 단위가 무엇인가 | 엔트리 수가 터무니없이 많거나 적음 |
| **컨테이너** | 롬이 통짜인가 파일시스템인가 | 바이너리 diff가 통째로 무의미해짐 |

## 2. 주소공간과 뱅킹

### 2.1 NES — CPU 주소 + 매퍼 뱅크

`asserted` PRG는 CPU $8000–$FFFF 창에 매핑된다. 창이 롬보다 작으므로 **매퍼가 뱅크를 갈아끼운다.**

핵심은 이거다: 같은 CPU 주소가 **실행 시점에 따라 다른 파일 오프셋으로 사상된다.**

```
file_offset = f(cpu_addr, 실행 시점의 뱅크 레지스터)
```

`derived` 이 함수는 정적 서술자(JSON 등)로 표현할 수 없다. 정적 레시피에는 실행 상태가 없기 때문이다.
따라서 **주소 변환은 데이터가 아니라 코드로 두어야 한다.** 이것이 이 프로젝트가 "JSON 서술자 단일화" 안을 기각한 실측 근거다.

### 2.2 SNES — LoROM / HiROM

`measured` LoROM 사상 공식:

```
file_offset = bank * 0x8000 + (cpu_addr - 0x8000)
```

`measured` 독립 사례 2건으로 검증(HK5 산출물의 기록값과 공식 계산이 정확히 일치):

| CPU 주소 | 공식 계산 | 기록된 롬 오프셋 | 판정 |
|---|---|---|---|
| `$0D:CE19` | `0x0D*0x8000 + 0x4E19` = `0x06CE19` | `0x06CE19` | 일치 |
| `$0E:BFEC` | `0x0E*0x8000 + 0x3FEC` = `0x073FEC` | `0x073FEC` | 일치 |

`documented` 내부 헤더 위치로 매핑 모드를 판별한다.

| 모드 | 헤더 오프셋 | `map_mode` |
|---|---|---|
| LoROM | `0x7FC0` | `0x20` |
| HiROM | `0xFFC0` | `0x21` |

`documented` 실측 예(북두의권5): `header_offset 32704`(= `0x7FC0`), `map_mode 32`(= `0x20`) → **표준 LoROM**, 크기 `1048576`(1MB).

> **함정** — 카피어 헤더 512바이트가 붙은 `.smc`는 모든 오프셋이 `+0x200` 밀린다. 헤더 유무를 먼저 판정하지 않으면 포인터 계산이 통째로 어긋난다. 크기가 `1048576`이 아니라 `1049088`이면 헤더가 붙은 것이다.

### 2.3 GBA / NDS / 3DS

`asserted` GBA는 카트리지가 `0x08000000`에 통짜 매핑된다. 포인터에서 `0x08000000`을 빼면 파일 오프셋이다. 가장 단순한 축.

`measured` NDS·3DS는 **주소공간 문제가 아니라 컨테이너 문제**다. 롬 내부가 파일시스템이라 포인터는 *멤버 파일 내부 상대 오프셋*이다. 3DS는 여기에 CTR 키스트림 암호화가 얹혀 통짜 바이너리 diff가 원리적으로 무의미하다.

→ 3DS류는 §7.3(트리 교체)로 간다.

## 3. 헤더와 정규화 — "다른 정규화는 다른 사실"

| 플랫폼 | 헤더 | 크기 |
|---|---|---|
| NES | iNES 매직 `NES\x1A` | 16바이트 |
| SNES | SMC 카피어 헤더(선택적) | 512바이트 |

`measured` 이 프로젝트가 정한 규율 — **해시를 두 개 따로 든다.**

- `rom_sha256` — 파일 그대로(as-is). 정체성.
- `normalization.body_sha256` — 헤더 제거 후. 비교용.

둘을 뭉개면 "헤더만 다른 같은 롬"과 "다른 롬"을 구분할 수 없고, 짝 개수가 부풀려진다.

## 4. 텍스트 저장 구조

### 4.1 포인터 테이블

`measured` 실측된 폭은 **2 / 3 / 4** 바이트다.

> **함정 — 폭 3.** SNES 24비트 롱 포인터가 여기 해당한다.
> `measured` 이 프로젝트는 초기에 폭 후보를 `(1,2,4,8)`로 뒀고, 그 결과 **SNES가 통째로 미검출**됐다. 스키마에 3이 없어서 검출기가 눈이 먼 것이다. 폭 목록은 읽기 폭(`1,2,4,8`)과 포인터 폭(`2,3,4`)을 **분리**해야 한다.

**엔트리 배치 두 종류** `measured`:

| kind | 뜻 | 예 |
|---|---|---|
| `offset_only` | 엔트리 = 포인터 하나 | stride 4, pointer_at 0 |
| `offset_size` | 엔트리 = 포인터 + 길이(+기타) | stride 16, pointer_at 8, size_at 12 |

`measured` **같은 포맷이 두 배치를 동시에 갖는다.** 실측 사례(3DS `msgb`):

```
messages : format=msgb  kind=offset_size  stride=16
keys     : format=msgb  kind=offset_only  stride=4
```

→ 포맷별 스칼라 stride 규칙은 **정상 데이터를 거부한다.** 레지스트리는 반드시 `FORMATS[format][kind]` 2단이어야 한다.

### 4.2 스케일드 포인터 — 가장 놓치기 쉬운 함정

`documented` 북두의권5의 포인터 테이블 서술:

```
rom_offset  0x06CE19   cpu_address $0D:CE19
entry_size  2
pointer_unit "half-byte-address (divide by 2 for ROM byte offset)"
```

**포인터 값 자체에 배율이 걸려 있다.** 저장된 값을 2로 나눠야 바이트 오프셋이 된다.

`derived` 이것이 위험한 이유는 실패가 조용하기 때문이다. 배율을 모르면 포인터 테이블을 정확히 찾아내고도 **모든 대상 주소가 2배로 빗나가** 텍스트가 안 나온다. 그러면 분석자는 "테이블을 잘못 찾았다"고 결론내고 맞는 답을 버린다.

`measured` **우리 스키마의 6번째 결함.** 현재 `recipe.py`는 `pointer_width` · `pointer_at` · `base`(주소공간 상수)만 표현한다. 포인터 **값의 배율**을 담을 필드가 없다. 즉 이 테이블은 우리 스키마로 서술 불가능하다.

> 필요한 최소 확장: `pointer_scale`(기본 1). 유효값은 관측된 것만 — 1, 2 정도로 시작하고 실측 없이 늘리지 않는다.

### 4.3 인코딩 — `.tbl`

`documented` 형식은 단순하다. 한 줄에 `바이트=글자`.

```
00=あ
01=い
02=う
...
```

`documented` 북두의권5는 195줄. 이 정도 크기면 가나 + 제어코드 + 약간의 한자 수준이다.

**왜 중요한가** `measured`: NES·SNES 텍스트는 ASCII가 아니라 **게임마다 다른 커스텀 타일 인덱스**다. `.tbl` 없이는 텍스트를 찾아도 못 읽는다. 그래서 diff만으로 하는 분석은 여기서 벽을 만난다 — §7.1의 교차증거가 필요한 이유다.

### 4.4 압축 — DTE / MTE

`asserted` 롬 용량이 부족하던 시절의 표준 기법. 자주 나오는 글자쌍(DTE)이나 단어(MTE)를 코드 하나에 접어 사전에 저장한다.

`documented` 실행 추적에서 **사전 접근이 별도 CSV로 분리**돼 나타난다(`dictionary_reads.csv`, 78행). 즉 사전 존재 여부는 추측할 게 아니라 **추적으로 확인되는 사실**이다.

`derived` 사전이 있으면 재삽입 난이도가 급등한다. 번역문을 넣을 때 사전을 재구축하거나 압축을 포기하고 공간을 확장해야 한다.

### 4.5 제어 코드

`asserted` 줄바꿈·대기·화자 전환·색상 등이 텍스트 스트림 안에 바이트로 섞인다. 문자표에 안 들어 있는 낮은 값 바이트가 후보다.

`documented` 북두의권5 리포트가 프로젝트의 핵심 관문으로 지목한 것이 정확히 이 셋이다 — **대사 코드표 · 제어 코드 · 포인터**. 폰트가 아니다.

## 5. 폰트와 타일

`documented` 실측된 폰트 서술:

```
rom_offset 0x073FEC   cpu_address $0E:BFEC
format     "16x16 1bpp quadrants (TL, TR, BL, BR)"
```

**16×16 글리프 하나가 8×8 사분면 4장으로 쪼개 저장된다.** `derived` 타일을 8×8 단위로만 가정하는 도구는 이걸 글자로 인식하지 못하고 노이즈로 버린다.

`asserted` 비트 깊이별 바이트 수(8×8 타일 기준): 1bpp 8바이트 · 2bpp 16바이트 · 4bpp 32바이트.

`documented` 폰트 위치 확정의 결정적 증거는 **DMA 추적**이다. 폰트는 VRAM에 업로드돼야 하므로 DMA 전송 로그에 반드시 나타난다.

## 6. 패치 포맷

| 포맷 | 성질 | 주의 |
|---|---|---|
| IPS | 오프셋+길이+바이트, RLE 지원 | 24비트 오프셋 → **16MB 한계** |
| BPS / UPS | 델타, 소스 해시 검증 포함 | 적용기 없으면 사다리가 `fetched`에서 멈춤 |
| xdelta | 범용 바이너리 델타 | 외부 도구 의존 |
| LayeredFS 트리 | 바이너리 diff가 아니라 **파일 교체 집합** | 3DS. diff 도구가 통째로 무의미 |

`measured` **IPS truncation extension** — 파서가 `{'size':0,'truncate':True}` 형태의 레코드를 만들고, 적용기가 대상 롬을 **늘린다.** 즉 IPS는 크기를 바꿀 수 있다.

`derived` 그래서 "패치 전후 크기가 같다"는 가정으로 짠 diff 도구는 이 경우 죽는다. 크기가 달라진 쌍은 바이너리 프로브 대상이 아니라 **별도 경로로 라우팅**해야 하며, 없는 필드를 0으로 합성해 억지로 통과시키면 안 된다.

`documented` 롬 확장은 정상 관행이다 — 2MB/4MB로 늘려 새 폰트와 스크립트를 넣고 IPS로 배포한다. IPS는 확장된 롬도 정상 패치한다.

## 7. 세 가지 방법론

무엇을 갖고 있느냐가 방법을 결정한다. 이게 이 문서의 실무적 핵심이다.

| 가진 것 | 방법 | 얻는 것 |
|---|---|---|
| 원본 롬 + 패치 | **A. 정적 diff 귀납** | 어디가 바뀌었나 |
| 원본 롬 + 에뮬레이터 | **B. 동적 실행 추적** | 누가 언제 읽나 |
| 패치만 / 트리 교체 | **C. 형태 귀납** | 포맷의 모양 |

### 7.1 방법 A — 정적 diff 귀납

**전제:** 원본 롬과 패치된 롬을 둘 다 갖고 있다.

절차:
1. 패치를 적용해 결과 롬을 만들고 **바이트 동일성**을 확인한다(`apply(base, patch) == result`).
2. 두 이미지를 비교해 변경 구간을 얻는다.
3. 변경 구간에서 **오름차순 정수 수열**을 찾는다 → 포인터 테이블 후보.
4. 후보가 가리키는 주소가 변경 영역에 착지하는지 본다 → 테이블 판정.

`measured` 이 접근이 실제로 잡아낸 실패 5건. 전부 **합성 픽스처로는 안 나오고 실측에서만** 나왔다:

1. **0xFF 패딩이 무한 오름차순으로 통과** — 오름차순 판정에 `>=`를 써서 같은 값이 이어지는 패딩을 수열로 인정했다. 결과: 4,234 엔트리 오탐.
2. **동점 처리 오류** — 주소공간 상수 후보가 동점일 때 잘못 골라 `base_delta=-285`.
3. **매핑 주소공간 미지원** — NES CPU 주소를 파일 오프셋으로 못 바꿔 검출 실패.
4. **커스텀 타일 인코딩 미대응** — 텍스트를 찾아도 못 읽음.
5. **폭 3 누락 → SNES 통째 미검출**(§4.1).

`measured` **수율의 현실.** IPS 51개 × 롬 348개 = **17,748회** 적용 + SHA-256 대조 → 증명된 JP→KR 쌍 **3건**. 그리고 그 3건에서도 미해석 바이트가 **72~86%** 남았다.

> 즉 정적 diff는 "어디가 바뀌었나"에는 답하지만 **"그게 무엇인가"에는 대부분 답하지 못한다.**

`measured` 읽을 수 없는 인코딩에 대한 우회: **가리켜짐 교차증거**(`pointed_to`). 글자를 못 읽어도, 포인터가 가리키는 위치가 변경 영역 안이라는 사실 자체가 증거가 된다. 단 이 증거는 별도 라벨로 분리 집계해야 한다 — 해석된 것처럼 합산하면 미해석률을 조용히 낮추는 자기기만이 된다.

> **방법 A의 원리적 한계 — 순환 논증 주의.**
> `measured` 프로브가 "변경 영역에 절반 이상 착지한 판독만" 방출하도록 게이트를 걸면, 그 출력은 "변경 영역과의 교차율이 절반 이상"이라는 검사를 **자동으로 통과**한다. 패치가 쓴 위치의 부분집합이 변경 위치이기 때문이다. 프로브 출력을 프로브 자신의 정답으로 쓰면 안 된다.

### 7.2 방법 B — 동적 실행 추적 (권장)

**전제:** 원본 롬 + 스크립팅 가능한 디버거(예: Mesen의 Lua).

`documented` 이 방법이 방법 A보다 강한 이유는 로그에 **`pc` 컬럼**이 있기 때문이다. 어떤 주소를 읽었는지만이 아니라 **어느 코드가 읽었는지**가 같이 남는다. "이 바이트가 무엇인가"라는 질문이 "이 루틴이 무엇인가"로 바뀌고, 후자는 역어셈블로 답할 수 있다.

`documented` 실측된 추적 산출물의 스키마:

| 산출물 | 컬럼 | 무엇을 답하나 | 실측 행수 |
|---|---|---|---|
| `rom_read_ranges.csv` | `window,start,end,bytes,total_reads,max_read` | 장면별로 읽힌 롬 구간 | 159 |
| `dma_trace.csv` | `frame,channel,dmap,bbad,source,length,vram_word` | VRAM 업로드 → **폰트 위치** | 2,264 |
| `text_reads.csv` | `frame,address,value,pc` | 텍스트 읽기 + 읽은 루틴 | 18,355 |
| `dialogue_buffer_writes.csv` | `frame,address,value,pc` | 대사 버퍼 조립 | 2,972 |
| `dictionary_reads.csv` | `frame,address,value,pc` | **DTE/MTE 사전 접근** | 78 |
| `script_rom_reads.csv` | `frame,address,value,pc` | 스크립트 원본 위치 | 53 |

`documented` 핵심은 **`window` 개념**이다 — 게임을 특정 장면(타이틀→이름입력 등)까지 몰고 가서 그 구간에만 읽힌 롬 범위를 잡는다. 시간을 축으로 써서 공간을 좁히는 것이다. 정적 분석에는 이 축이 아예 없다.

`documented` 대사 데이터는 WRAM 버퍼(`$7E0700` 대역)에 조립되며, 그 쓰기를 일으킨 PC를 따라가면 대사 인터프리터에 도달한다. 스크립트 원본은 롬 `$09ED62` 부근에서 읽히고 그 읽기의 PC가 인터프리터를 지목한다.

**권장 순서** `documented`:
1. 디버거로 **폰트 DMA와 문자 출력 루틴**을 확정
2. 문자표와 제어 코드 복원
3. 대사 덤퍼 작성
4. 포인터 테이블·이벤트 명령 분석
5. 전체 스크립트 추출
6. 롬 확장(2MB/4MB)
7. 한글 폰트·디코더 구현
8. 재삽입 도구
9. 화면별 테스트(메뉴/전투/이벤트)
10. 체크섬 수정 + 패치 생성

`documented` 이 순서의 요점은 **폰트를 먼저 하는 게 쉬워서가 아니라, 폰트 DMA가 문자 출력 루틴으로 가는 가장 짧은 실마리이기 때문**이다. 실제로 이 프로젝트의 난이도 평가도 폰트를 최하(★★)로, 스크립트 추출과 포인터를 최상(★★★★)으로 매겼다.

**검증 관행** `documented`: 패치 전후 VRAM을 각각 덤프해 비교한다(각 65,536바이트). 화면 출력이 실제로 바뀌었는지를 **캡처 이미지가 아니라 메모리 상태**로 확인하는 것이다.

**최소 개입 탐침** `documented`: 전체를 바꾸기 전에 **글리프 1개만** 교체해보고(예: 인덱스 0을 한글 한 글자로) 화면에 그 글자가 뜨는지 본다. 뜨면 폰트 위치·포맷·출력 경로가 한꺼번에 증명된다. 안 뜨면 셋 중 하나가 틀린 것이고 아직 아무것도 낭비하지 않았다.

### 7.3 방법 C — 원본 롬 없이 (형태 귀납)

**전제:** 원본이 없거나(재고 부재), 애초에 바이너리 diff가 무의미한 경우(3DS LayeredFS).

`measured` 실측 사례 — 3DS 타이틀의 텍스트 멤버 576개를 롬 없이 형태만으로 귀납:

- 기대 형태와 일치: **561 / 576 (97.4%)**
- NUL 종결자 확인: **457 / 550 (83.1%)**

`derived` 이 방법의 산출물은 **가설(`asserted`)이지 증명이 아니다.** 원본 대조가 없으므로 등급을 올릴 수 없다. 그래서 이 등급의 결과는 성과 지표나 선택 기준에 넣으면 안 된다 — 자기 확신만 부풀린다.

`measured` 다만 트리 교체는 **원본 롬 없이도 진행 가능한 유일한 라인**이므로, 재고에 일본판이 없는 상황에서는 이쪽이 주경로가 된다.

## 8. 증거 사다리와 검증 규율

`measured` 이 프로젝트가 쓰는 사다리. **한 칸씩만** 올라가며 각 칸에 필수 증거가 있다.

```
discovered → fetched → applied → probed → confirmed
```

| 칸 | 필수 증거 |
|---|---|
| `discovered` | 출처 |
| `fetched` | 패치 해시, 바이트 수 |
| `applied` | 원본 해시(as-is), 결과 해시, 정규화 기록 |
| `probed` | 가설 해시, 구간, **미해석 바이트 + 그 분모**, 정렬 상태 |
| `confirmed` | 독립 측정에 의한 왕복 증명 |

`measured` **현재 도달 천장은 `probed`다.** 프로브가 낸 결과를 프로브 자신이 확인할 수 없으므로 `confirmed`로 갈 수 없다. 독립 측정 수단(=방법 B의 런타임 추적)이 없으면 이 칸은 구조적으로 비어 있다.

> 이 문서에서 방법 B를 권장하는 진짜 이유가 이것이다. **`confirmed`를 여는 유일한 열쇠**다.

### 검증 규율 5개

1. **비율에는 반드시 분모를 붙인다.** "미해석 80%"는 분모 없이는 아무 뜻도 없다. 이미지 전체 대비인지, 변경 바이트 대비인지에 따라 완전히 다른 사실이다.
2. **측정 없이 빨라졌다고 쓰지 않는다.** 측정치가 없으면 `unmeasured`라고 쓴다. 이건 실패가 아니다.
3. **결정론.** 같은 입력으로 두 번 돌려 산출물이 바이트 단위로 같아야 한다. 다르면 그 산출물은 증거가 아니다.
4. **판정값과 관측값을 분리한다.** 도구가 `compounding: true` 같은 **판정을 방출하면 그게 곧 주장**이다. 근거가 없으면 판정 필드 자체를 없앤다 — "항상 false로 고정"은 슬롯을 남겨 언제든 되살아난다.
5. **제작자 1인 = 1표.** 같은 사람이 만든 패치 20개는 근거 20개가 아니라 1개다.

## 10. 부록 — 워크플로 골격

`documented` 실측 사례가 쓴 단계 구성. 각 단계가 **판정(PASS/FAIL)이 있는 상태 보고서**를 남긴다.

| 단계 | 내용 | 산출물 성격 |
|---|---|---|
| 0 | 롬 무결성·헤더·매핑 확인 | 해시 4종 + 헤더 필드 |
| 1 | 폰트 탐침(글리프 1개 교체) | PASS/FAIL + 교체 전후 해시 |
| 2 | 문자표·포인터 구조 확정 | `.tbl` + 포인터 서술 |
| 3 | 스크립트 덤프 | 대사 카탈로그 |
| 4 | 번역 + 감사 | 배치별 감사 로그 |
| 5 | UI 시험 적용 | 화면별 리포트 |
| 6 | 전체 패치 + 런타임 검증 | 패치 + 실행 결과 |

**모든 산출물이 `source_rom_sha256`을 품는다.** `documented` 어떤 원본에 대한 사실인지가 산출물 자체에 박혀 있으면, 나중에 다른 롬과 섞이지 않는다. 이건 사소해 보이지만 라벨 거짓이 상수인 이 바닥에서는 결정적이다.

## 11. 미해결

정직하게 남긴다.

- `measured` **일본판 원본 재고 부재.** NAS 롬 4세트(최대 30,150개 / 628GB)가 사실상 전부 한글패치 플레이셋이다. NDS·3DS 원본은 0. GBA 원본 10개는 전부 US판.
- `measured` 북두의권5의 일본판 SNES 롬(`sha256 4d68c107…f28b3`)은 **NAS 카탈로그에 없다.** SNES 항목 223건 중 Hokuto 계열 SNES는 0건. 이 타이틀은 현 재고로 방법 A·B 둘 다 불가.
- `measured` `confirmed` 0건. 독립 측정 경로가 없어 사다리 최상단이 구조적으로 비어 있다.
- `measured` 미해석률 72~86%가 그대로 남아 있고, 이걸 줄이는 것은 현재 목표가 아니다(줄이는 척하는 게 더 나쁘다).
- `measured` 스키마가 `pointer_scale`을 표현하지 못한다(§4.2). 실측으로 확인된 결함이며 아직 안 고쳤다.
